## 第 0 章：为什么需要 MIPI —— 从并行到串行的必然

### 0.1 摄像头接口的三代演进

早期摄像头用 **DVP 并行接口**：一根像素时钟线 + 8~12 根数据线 + 场/行同步线，
一次并行送一个字节。问题在哪？**当分辨率/帧率上去，时钟频率必须跟着涨，
而多根线同时翻转时，各线之间到达时间差（skew）会越来越大**——100MHz 以上
并行线就极难做等长匹配，且几十根线同时翻转的电磁干扰（EMI）很大、功耗高。

于是业界转向**串行差分**：用少量"高速差分对"把数据一位一位地快速送出去。
MIPI（Mobile Industry Processor Interface，移动产业处理器接口联盟）定义的
**CSI-2**（Camera Serial Interface 2）就是摄像头领域的标准，
它跑在 **D-PHY**（物理层规范）之上。

### 0.2 差分的本质：为什么两根线而不是一根

一根线传信号，接收端判断"电压高于某阈值=1，低于=0"——那么线上叠加的任何
干扰（噪声）都可能翻转判断。**差分**用两根线传**一对反相信号**：
接收端只关心两者的**差**。外界干扰（闪电、电源纹波、邻线串扰）通常会
同等地耦合到两根线上（共模），相减就被抵消；而有用信号是反相的，
相减变为两倍。**代价是线数×2，换来的是抗干扰、低摆幅（更快）、低 EMI。**

### 0.3 本工程的物理连接

SC500CS 配置为 **2-lane**，即：
- **1 对时钟线**：MCP/MCN（Clock Lane，差分）；
- **2 对数据线**：MD0P/N、MD1P/N（Lane 0/1，差分）。
共 6 根信号线，代替 DVP 时代的十几根——这就是"差分省线"的直观收益。

> 对照代码：`design_top_wrapper.v` 例化 `mipi_dphy_rx_ph1p_mipiio_wrapper`
> 时 `.LANE_NUM(2)`，引脚 `IO_rx_clk_pad_p/n`、`IO_rx_data_pad_p/n[3:0]`
> 就是这些差分对。PH1P35 芯片**内置 D-PHY 硬核**（这是选这颗芯片的原因
> 之一），硬核的差分接收、时钟恢复等电气工作不用我们写。

### 0.4 "lane"到底是什么——为什么总是"2-lane""4-lane"

**lane 的本义就是"车道"**（马路上的一条行车道），MIPI 直接借用了这个词，
而且比喻极其贴切：

- **一条 lane = 一条串行通道 = 一对差分线**。这两根线（P 和 N）是同一个
  信号的正反两面，**合起来才算一条 lane**，不是两条独立通道（差分的道理
  见 0.2 节：接收端只看两者之差）。
- **数据比特像车**：一条 lane 就是一条车道，比特只能一辆接一辆地单列
  通过（这就是"串行"）。两条 lane 就是两条车道并行，同一位时间内可以
  同时"各过一辆车"——**吞吐翻倍**。

```
时间→    B0   B1   B2   B3   B4   B5   B6   B7 …
          │    │    │    │    │    │    │    │
lane0:    ●─────────●─────────●─────────●──────→   B0, B2, B4, B6 …
lane1:         ●─────────●─────────●─────────●──→   B1, B3, B5, B7 …
```

（读法：字节**轮流分发**——B0→lane0、B1→lane1、B2→lane0、B3→lane1……，
接收端按同样规则把两条车道的数据**合并还原**成原始字节序。）

用代码里的事实验证这个模型：

- `design_top_wrapper.v` 例化硬核时写的是 `.LANE_NUM(2)`——**用几条
  车道（几条数据线）**；`.BYTE_NUM(1)`——每条车道每拍出一个字节；
- 所以硬核输出 `O_hs_rx_data` 宽度 = `LANE_NUM×BYTE_NUM×8` = **16 位**
  （2 车道 × 1 字节），这就是 `csi_unpacket_2lane.v` 输入注释里
  "2LANE，1BYTE模式"的含义；
- `csi_unpacket_2lane.v` 再"每 2 个 16 位拼 1 个 32 位"，是因为**两拍
  才凑满 4 个字节**（车道多≠单拍变宽，只是同拍并行）；
- 硬核内部还有 `channel_aligner`（通道对齐器）——**把多条车道的到达
  对齐**：lane 之间走线长度不同、延时不同，不对齐就把 B0 B1 B2 B3 拼成
  B1 B0 B3 B2，画面就花了。所以"lane 数""lane 延时""lane 极性反转"
  都是硬核的参数（`I_lane_invert`、`I_data_laneX_in_delay`）。

**为什么是 2 条而不是 1 或 4 条**：SC500CS 手册推荐 ≤1.0 Gbps/lane；
本工程一帧 1280×720×10bit ≈ 9.2 Mbit，按 30fps 约 276 Mbps 总载荷，
分到 2 条 lane 每条约 138 Mbps（含开销更低），**完全跑不满**——2 条是
够用且省引脚的选择。车道越多：理论带宽越高，但引脚/走线/功耗都涨，
且需要 sensor 和 FPGA 都支持。

## 第 1 章：D-PHY 的两种"人格"——LP 模式与 HS 模式

### 1.1 为什么一条 lane 要分两种模式

摄像头大部分时间**没在传像素**（帧与帧之间、行与行之间有空闲），但偶尔要
传控制信息（同步事件）。如果一直用高速差分模式传这些零星信息，功耗就白白
浪费（高速电路本身就费电）。MIPI 的设计哲学：**传大数据时用高速模式
（HS，High-Speed），传控制/空闲时切换到低功耗单端模式（LP，Low-Power）**，
同一对线上分时复用两套电气规范。

| | LP 模式 | HS 模式 |
|---|---|---|
| 电气形态 | 单端（两根线各自对地） | 差分（两根线之间） |
| 电平摆幅 | 0~1.2V（大，抗干扰但不快） | 约 ±200mV（小，快） |
| 速率 | 约 10 Mbps 量级 | 每 lane 可达 1 Gbps+ |
| 用途 | 进入/退出高速、控制信号 | 像素数据突发传输 |

### 1.2 一次数据传输的完整"仪式"（HS 进入序列）

一条 lane 从空闲到传数据，要经过一个固定的握手序列
（这就是为什么需要硬核/专业的 PHY IP 来处理——纯逻辑很难做）：

```
LP-11（空闲） → LP-01 → LP-00 → [HS-0] → Sync序列(0xB8) → 负载数据 → ……
```

- 接收端靠 **HS 切入序列（LP→HS 的跳变模式）** 判定"高速数据来了"；
- **Sync 序列**是一个固定的字节 **0xB8**，用于**字节对齐**——因为串行
  接收器恢复时钟后不知道从哪里切字节，这个固定 pattern 就是"起跑线"。
  硬核里的 `byte_aligner`（字节对齐器）和 `channel_aligner`（通道对齐器）
  就是干这个的；
- 结束时用 EoT（传输结束）序列回到 LP-11 空闲。

### 1.3 时钟线的 DDR 特性

时钟线在 HS 模式下**持续翻转**（即使在传字节间隙），数据线在**时钟的
双沿**采样（DDR，双倍数据率）。接收器用时钟线恢复出的时钟对数据线
采样——这就是输出信号名叫 `O_hs_rx_clk`（恢复时钟）的原因：
**这个时钟不是外部给的，是从数据流里"恢复"出来的**。

> 对照代码/工程：
> - `mipi_dphy_rx_ph1p_mipiio_wrapper` 的参数里 `HS_EQUALIZER("0dB")`、
>   `HS_VGA_GAIN("8dB")` 是**接收端均衡/增益**调节——高速信号经过板子和
>   线缆会衰减变形，用模拟均衡补偿，这是硬件调试的旋钮；
> - `I_clk_lane_in_delay` / `I_data_laneX_in_delay` 是**各 lane 的延时调节**
>   （代码里都填 6'd0）——板子走线不等长导致 lane 间错位时，靠这个对齐；
> - `I_lane_invert` 用于**差分对极性接反时的软件补救**（P/N 接反是常见
>   硬件错误，接反了让这里置位即可，不用改板）。

### 1.4 硬件排障的两个直觉

1. **画面全黑/无数据**：先查 HS 进入序列是否发生——可以借助 `O_lane_error`
   信号（代码里接出来变成 `S_lane_error`）判断 lane 通信是否异常；
2. **画面有规律撕裂/错位**：多半是 lane 间对齐或延时问题（0xB8 对齐失败、
   两 lane 错拍），此时调 `in_delay` 或检查硬核配置。

## 第 2 章：CSI-2 协议层——数据是怎么"打包"的

### 2.1 协议的层次观

```
应用层：     一帧图像（1280×720 个像素）
传输层：     CSI-2 把像素流切成"包"（Packet），一帧 = 帧起始短包 + N 行长包 + 帧结束短包
物理层：     D-PHY 把这些字节以 HS 模式串行送出
```

**为什么要打包而不是裸流**？因为接收端需要知道：数据何时开始、何时结束、
多长、什么格式、是否出错——这些"元信息"（metadata）必须和数据混在一起传，
包结构就是它们的载体。

### 2.2 两种包：短包与长包

**短包（4 字节）**——只传事件和少量信息，字段如下：

```
字节0: DI  = VC[7:6] | DT[5:0]   （虚拟通道 + 数据类型）
字节1: WC 低 8 位                （帧号 for FS/FE）
字节2: WC 高 8 位
字节3: ECC                       （对前 3 字节的纠错码）
```

短包的 DT 编码（手册表 1-8，也是 `csi_unpacket_2lane.v` 开头注释照抄的）：

| DT | 含义 |
|---|---|
| 0x00 | **Frame Start**（帧起始） |
| 0x01 | **Frame End**（帧结束） |
| 0x02 / 0x03 | Line Start / Line End（行起始/结束，本工程没用） |

**长包**（传图像数据）：

```
包头 4 字节: DI + WC低 + WC高 + ECC     ← 与短包同构
载荷:        WC 个字节的图像数据           ← 真正的像素字节
包尾 2 字节: CRC16                       ← 载荷校验
```

- **DT=0x2B** → 载荷是 RAW10 格式（10 位像素打包流）；
- **DT=0x2A** → RAW8；本工程用 0x2B（`uics500reg.v` 把 0x3031 写成 0x0a
  配置传感器输出 RAW10）；
- **WC（Word Count）** = 载荷字节数。对一行 1280 像素的 RAW10 数据：
  1280×10bit ÷ 8 = **1600 字节**，即一行一个长包（实测拆包逻辑按 5 字节
  /4 像素一小组推进，见第 3 章）。

### 2.3 VC 与 ECC 的存在感

- **VC（Virtual Channel）**：一条 MIPI 链路上可以交织多个数据流（如
  主图+深度图），用 2 位 VC 区分。单摄像头场景恒为 0，所以代码里直接
  忽略高 2 位；
- **ECC**：对包头 3 字节的检错纠错，保证"包头错了还知道错"；
- **CRC16**：对长包载荷的校验——本工程的代码**不校验**（直接剥掉），
  这是简化处理：比赛场景可以不做，量产设计里应当校验并统计错误率。

### 2.4 一帧的完整字节流全景（2-lane）

```
[FS短包 4B] → [长包: 包头4B + 载荷1600B×720行 + CRC2B]×720 → [FE短包 4B]
```

**2-lane 交错规则**：字节轮流分发到两条 lane——
Byte0→lane0，Byte1→lane1，Byte2→lane0，Byte3→lane1……
（手册图 1-14）。也就是**同一时刻两条 lane 各送一个字节**，
接收端每个时钟周期收到 2 个字节。

> 对照代码：`csi_unpacket_2lane.v` 的输入 `I_hs_data[15:0]` 正是
> "2 lane × 1 字节"的 16 位——每个周期 2 字节，这就是名字里
> "2LANE，1BYTE模式"的含义（见该文件第 42 行注释）。

## 第 3 章：RAW10 的紧排格式——4 像素怎么塞进 5 字节

### 3.1 为什么要打包：10 位不是 8 的整数倍

传感器每个像素是 10 位（0~1023）。总线是字节（8 位）为单位的，
如果每像素占 2 字节（16 位），就浪费了 6 位——数据量涨 60%。
MIPI 的解法：**把 4 个像素拼成 5 字节**：

```
字节0: P0[9:2]       （像素0的高8位）
字节1: P1[9:2]       （像素1的高8位）
字节2: P2[9:2]
字节3: P3[9:2]
字节4: {P3[1:0], P2[1:0], P1[1:0], P0[1:0]}   （4个像素各自的低2位拼成1字节）
```

4×10=40 位 = 5×8=40 位，一个比特不浪费。**代价是解包逻辑变复杂**：
接收端必须知道字节流里"第 5 个字节"的位置（相位），因为每 5 字节里
前 4 字节是"高位"，第 5 字节是"低位拼包"。

### 3.2 相位问题的本质与代码解法

字节流连绵不断，"哪个字节是 5 字节组的第 0 个"这个相位问题不会自己
消失。**好消息**：长包结构死板——包头 4 字节 + 载荷，载荷起点固定，
只要对齐到包头，载荷相位就确定了。

代码 `raw10_unpacket_2lane.v` 用了一个**5 状态计数器 S_cnt（0~4）**
循环推进，把连续字节流按 5 字节一组切割（详见 3.3）。

### 3.3 逐位推导：S_cnt=0 时发生了什么

先明确数据形态：`csi_unpacket_2lane.v` 把 2 个 16 位拍拼成 **32 位**
（4 字节）输出，所以 raw10_unpacket 每拍看到 **4 个字节**。

以 32 位数据为 `{B3,B2,B1,B0}`（B0 最早）为例，5 字节组布局为：

```
组内字节序号:  0      1      2      3      4
内容:        P0高位  P1高位  P2高位  P3高位  低位拼包
```

**S_cnt=0 的代码**（第 89-95 行）：

```verilog
S_raw10_wr_data[39:30] <= {S_csi_data_2d[31:24], I_csi_data[25:24]};  ///P0
S_raw10_wr_data[29:20] <= {S_csi_data_2d[23:16], I_csi_data[27:26]};  ///P1
S_raw10_wr_data[19:10] <= {S_csi_data_2d[15 : 8], I_csi_data[29:28]};  ///P2
S_raw10_wr_data[9:0]   <= {S_csi_data_2d[7 : 0], I_csi_data[31:30]};  ///P3
```

解读：`S_csi_data_2d` 是**两拍前**的数据（延迟寄存器），
`I_csi_data` 是**当前**拍的数据。P0 = "两拍前的高 8 位" + "当前拍的
[25:24]两位"——这就是**把分组内'高位字节'与'低位拼包字节'对齐**的动作。
20 字节（5 拍×4 字节）进来，16 像素（4 拍×4 像素）出去。

### 3.4 输出重排的深意

最后输出（第 134-139 行）：

```verilog
O_raw10_data <= {S_raw10_wr_data[9:0],   // P3 排到最高位
                 S_raw10_wr_data[19:10], // P2
                 S_raw10_wr_data[29:20], // P1
                 S_raw10_wr_data[39:30]};// P0 排到最低位
```

拼包时 P0 在最高位（[39:30]），输出时**换到最低位** [9:0]。
这是为了和下一级（uial2axis → demosaic）约定的**像素序**一致：
低位在先。这个"内部低位先行、进 DDR 打包前再反回高位先行"的约定
是全工程像素序纪律的一部分（见 HANDOFF.md §3 契约 10）。

### 3.5 被注释掉的 RAW8 路径（第 141-233 行）

代码里保留了一段注释掉的"RAW10→RAW8"逻辑：减黑电平（`I_camera_black_level`）
后右移 2 位，再进 FIFO 跨过行消隐。**本工程没启用**——因为下游
demosaic 按 RAW10 输入设计。理解它存在过，能帮你理解一类设计选择：
10 位精度 vs 数据量，最终工程选择了保精度（10 位全给 demosaic）。

## 第 4 章：电路层的最后一环——包怎么变成"干净的像素流"

### 4.1 uial2axis：帧/行坐标的生成器

`raw10_unpacket_2lane.v` 的输出是 40 位（4 像素×10 位）"裸流"，
还缺一样东西：**接收端怎么知道哪拍是行首、哪帧是帧首**？
帧起始短包（FS）早就在 csi_unpacket 阶段被剥出来了，但**长度会漂移**
（哪一拍算行首需要数拍子）。

`uial2axis.v` 就是计数员（84 行，很简单但极关键）：

```verilog
localparam IMG_WIDTH_4X = (IMG_WIDTH >> 2);   // 1280/4 = 320 拍/行
assign axis_tlast  = hcnt == IMG_WIDTH_4X-1 && axis_tvalid;  // 每320拍一行尾
assign axis_tuser  = vcnt == 0 && hcnt == 0 && axis_tvalid;  // 第一行第一拍=帧首
```

- **hcnt 数拍**：0~319 循环，第 319 拍拉 tlast（行尾）；
- **vcnt 数行**：0~719 循环，配合 hcnt 形成 tuser（帧首）；
- 于是输出流带上了 **AXI4-Stream 的三标志**：tvalid/tuser/tlast——
  **这是全工程所有下游模块（demosaic、算法、FIFO）的公共语言**。

**⚠️ 尺寸参数的分工**（改分辨率时必看）：
`uial2axis` 的 `IMG_WIDTH/IMG_HEIGHT` 参数是"数拍子的尺子"，
必须与传感器输出窗口和 `image_correction` 的裁剪范围三者一致（都改成
1280×720），任何一处不一致 → 行切片错位 → 画面撕裂/错位。

### 4.2 image_correction：FPGA 侧的"取景框"

传感器已经只输出 1280×720 窗口（在传感器内部裁剪，见手册表 2-8），
那这级还有什么用？——**丢行消隐**。

摄像头一行结束到下一行开始之间、以及帧之间，总线上仍有短暂停顿/
多余字节。`image_correction.v` 用一个 `cnt==10` 的间隙计数器检测行间隔，
维护自己的行计数 v_cnt、列计数 h_cnt，**只放行 720 行 × 320 拍窗口内的
数据**，窗口外一律清零（`O_raw_tdata = V_valid && H_valid ? ... : 0`）。

它还要输出内部生成的三标志（tuser/tlast/tvalid）——这是**第二次**
生成（第一次在 uial2axis），为什么？因为 `image_correction` 是"选择性
放行"，放行后的拍子可能不连续，所以必须在放行侧重新生成标志。

> 这段代码就是之前"720p 乱码"事故的发生地：裁剪常数 255/599 是
> 1024×600 时代的，改成 1280×720 时忘了同步改 → 每行只放行 256 拍、
> 只放 600 行 → 画面错位。修复=改成 319/719。**这是"改分辨率全耦合点"
> 清单里的一员**（见记忆 resolution-change-720p）。

## 第 5 章：五级链路的整体视角（为什么是这个顺序）

```
传感器引脚（差分对）
  │ [D-PHY 硬核]      电气层：恢复时钟、字节/通道对齐       ← 芯片替你干
  │ [csi_unpacket]    协议层：剥包壳（FS/FE/包头/CRC）      ← 手写 138 行
  │ [raw10_unpacket]  格式层：5字节/4像素 → 4像素/拍        ← 手写 235 行
  │ [uial2axis]       坐标层：数拍子，标出帧首/行尾          ← 手写 84 行
  │ [image_correction]窗口层：丢弃消隐，只留有效区域          ← 手写 97 行
  ▼
ISP/算法/DDR/HDMI（都在 1280×720×10bit 的约定下工作）
```

这五级的设计体现了一个通用原则：**每一级只做一件事，接口用计数器约定
（拍数、行数），把"事件语义"（帧首/行尾）翻译成"位置语义"（第几拍）**。
下游所有模块都靠"每行 320 拍、每帧 720 行"这个约定活着——这就是为什么
它被写进 HANDOFF.md 的关键契约第 2 条（"违反复现已修 bug"清单）。

### 配套实验建议（手上有板子时）

1. **看总线**：把万用表放一边，用示波器/逻辑分析仪单端探针触碰 MD0P
   （低占空比的小摆幅就是 HS 突发，帧间隔能看到回归高电平的空闲），
   直观感受"帧与帧之间的空闲期"；
2. **数包**：在 `csi_unpacket_2lane.v` 的 `O_csi_frame_start` 上接
   计数器（或仿真里断点），确认每帧恰好一次 FS；
3. **仿真实验**：给 `raw10_unpacket_2lane` 喂 3.3 节的 5 字节序列，
   看输出 4 像素的 10 位值是否与手工拼接一致——这是理解相位问题最快
   的动手方式。
